Мастер-пароль и Touch ID: кто что защищает

Как устроена защита сохранённых паролей БД и SSH-passphrase, зачем нужны оба фактора и почему нельзя обойтись одним Touch ID.

Если коротко

Все секреты шифруются одним ключом — DEK. К нему ведут две двери. Мастер-пароль — криптографическая дверь: защищает секреты математически и офлайн, работает где угодно, но незаменим. Touch ID — дверь присутствия: быстрый вход на этом Mac, но его можно потерять без последствий. Пароль — фундамент, Touch ID — ярлык поверх него.

01Центр всего — DEK

При первом запуске приложение генерирует случайный 256-битный ключ — DEK (Data Encryption Key). Им, через AES-256-GCM, зашифрованы все секреты одним блобом в файле vault.json. Больше DEK ничего не «знает» — он просто ключ. Разблокировка приложения = получить DEK в память на сессию. А к самому DEK ведут ровно два пути:

Две независимые двери к одному ключу. У каждой — своя защита.

02Кто шифрует, кто кует ключ

Частый вопрос: «а не зашифровать ли и сами данные через Argon2?». Нет — и вот почему это невозможно в принципе, а данные при этом и так под защитой Argon2.

▲ Argon2 не шифрует

Argon2 — односторонняя функция, выдаёт фиксированные 32 байта. «Прогонишь vault.json через Argon2» — получишь хеш, а данные исчезнут навсегда, расшифровать нечем. Шифрование обязано быть обратимым; Argon2 нарочно необратима. Это как «пилить доску термометром» — не тот инструмент. Шифрует всегда AES-256-GCM; Argon2 только кует из пароля ключ для него.

Данные уже под зонтиком Argon2. Единственный путь к DEK из пароля идёт через шаг pwWrap = AES-GCM(Argon2id(пароль), DEK) — то есть перебор пароля упирается в дорогой Argon2 (≈19 МБ + время на попытку). Секреты наследуют эту защиту автоматически. Добавлять «ещё Argon2» некуда: узкое место — энтропия пароля, а она уже захеширована один раз; второй прогон лишь удвоит время разблокировки тебе, без выигрыша в стойкости.

Зачем вообще слой DEK

Логичный следующий вопрос: почему не шифровать секреты прямо ключом из пароля, без промежуточного DEK?

С DEK наш вариант «Прямой» без DEK
Схема AES(Argon2(pw), DEK) + AES(DEK, data) AES(Argon2(pw), data)
Смена мастер-пароля перешифровать 32 байта DEK перешифровать все секреты
Две двери (пароль и Touch ID) обе достают один DEK → одни и те же секреты нужны две полные копии зашифрованных секретов, синхронить вручную
◆ Ради чего DEK и существует

Touch ID без DEK не сделать. И пароль, и палец должны привести к одному ключу, которым расшифрованы секреты. DEK — тот единственный общий ключ, что отпирают обе двери: пароль оборачивает его в pwWrap, keychain хранит его копию под Touch ID. Убери DEK — придётся держать два зашифрованных дубля секретов и держать их в синхроне.

03Мастер-пароль — криптографическая дверь

В vault.json лежит pwWrap = AES-GCM(Argon2id(пароль), DEK) — то есть DEK, «обёрнутый» ключом, выведенным из твоего пароля.

Что защищает

Сам DEK «на диске», математически. Без пароля этот блоб — бесполезный шум. Argon2id делает перебор дорогим (каждая попытка ≈ 19 МБ памяти + время), так что даже слабоватый пароль трудно ломать.

От чего защищает

От того, у кого есть твои файлы, но нет тебя: утёк vault.json в облачный бэкап, украли диск, синкнул в dotfiles, чужой процесс прочитал файл. Секреты не достать.

◆ Ключевое свойство

Не зависит ни от чего — ни от Mac, ни от ОС, ни от keychain. Чистая криптография, работает на любой машине. Поэтому же и невосстановим: живёт только у тебя в голове, «забыл пароль» = потерял секреты.

04Touch ID — дверь присутствия

Это не более сильная дверь, а более быстрая — шорткат, чтобы не печатать пароль. Копия DEK лежит в login keychain, и её стерегут три слоя сразу (Touch ID — лишь один из них):

СлойЧто делаетОт чего защищает
Шифрование login keychain keychain зашифрован ключом от пароля аккаунта macOS другой Mac / выключенный / разлогиненный — копия DEK нечитаема
ACL по подписи («Always Allow») читать запись может только подписанный sql-tauri чужое / вредоносное приложение на твоём же маке
Touch ID (LAContext) требует живой палец (fallback — пароль аккаунта) человек за твоим разблокированным маком
◆ Ключевое свойство

Привязана к железу: работает только на этом Mac, под этим аккаунтом, для этой подписи. Скопируешь keychain на другую машину — мёртво. Зато защищает от того, у кого есть твой Mac, но нет твоего пальца.

05Как они соотносятся

Мастер-пароль — корень доверия (источник). Touch ID — кэшированный ярлык поверх него.

→
Пароль всегда выводит DEK

Это математика — работает всегда и везде. Touch ID работает, только если DEK заранее положили в keychain, а положить его можно, лишь разблокировав паролем.

→
Touch ID теряется без последствий

Новый Mac, сброс keychain, сменил отпечаток — падаешь на пароль, ничего не потеряно. Пароль незаменим, Touch ID расходуем.

Аналогия: пароль — сейф с кодовым замком (взломостойкий, но код надо помнить). Touch ID — дубликат кода в запертом по пальцу ящике стола: быстро, но только у тебя дома и пока стол твой.

06Почему нельзя обойтись только Touch ID

Потому что Touch ID — это не ключ, а вертушка «да / нет». И на этом всё упирается.

▲ Отпечаток не может быть ключом — принципиально

Из пальца нельзя вывести ключ шифрования: отпечаток считывается каждый раз чуть по-разному, его нельзя сменить/отозвать, а Secure Enclave вообще никогда не отдаёт биометрию наружу. Touch ID умеет одно — ответить «человек тут? да/нет». Значит, настоящий ключ всё равно должен где-то лежать, и его надо чем-то защитить в покое. Защищает его... пароль (пусть даже пароль аккаунта macOS). Чистого «только Touch ID» не существует — даже системный Touch ID всегда падает на пароль.

1
Нужен bootstrap

Чтобы положить DEK в keychain (включить Touch ID), надо его уже иметь. На первом запуске DEK ещё нет — кто-то должен создать и защитить его первым. Это и есть пароль. Touch ID всегда появляется вторым.

2
Переносимость и бэкап

vault.json — обычный файл: бэкапишь, синкаешь, переносишь на другой мак. Пароль делает его пригодным где угодно. Touch-ID-only привязал бы всё к Secure Enclave одного ноутбука без пути назад.

3
DEK-в-keychain — это кэш, а не источник

Кэш без источника = единая точка отказа. Любой из случаев ниже уничтожил бы секреты безвозвратно:

  • новый Mac / переустановка macOS — keychain не переносится
  • keychain сбросился или побился
  • сменил / переоформил отпечатки
  • сдохло железо Touch ID

С паролем же ты всегда выведешь DEK заново из pwWrap — на любой машине. Поэтому правильная схема — не «пароль или Touch ID», а «пароль как фундамент + Touch ID как быстрый вход, который не жалко потерять».

07Честный нюанс реализации

◆ Где именно проходит криптозамок

В нашей реализации Touch ID навязывает приложение (через LAContext), а не сам keychain. То есть настоящий криптозамок на копии DEK — это ACL по подписи, а Touch ID — слой присутствия/UX поверх него. Платный «data-protection keychain» путь навязывал бы биометрию самим keychain (строже — палец нельзя обойти в принципе), но требует Apple-профиля с годовым сроком. Мы сознательно выбрали бесплатную схему, работающую везде, — а корневую offline-защиту всё равно держит мастер-пароль, который никуда не девается.
