sql-kai — CLI к sql-kai

Консольный клиент поверх того же Rust-ядра, что и приложение sql-kai: общие профили подключений, ssh-туннели, vault с паролями и история запросов. Собирается из этого же репозитория (src-tauri, cargo-фича cli).

Быстрый старт

sql-kai profiles list                       # какие профили уже есть (общие с GUI)
sql-kai domainator -c "SELECT count(*) FROM domains"
echo "SELECT now()" | sql-kai orchestrator  # SQL со stdin; или -f query.sql
sql-kai coordinator -c "..." --json         # структурный вывод: числа/bool/null/json типизированы
sql-kai tables coordinator --counts         # таблицы + примерное число строк

sql-kai <alias> … — сокращение для sql-kai q <alias> …. alias — имя, id или группа профиля.

Установка

С этой машины (из репозитория)

cd ~/Projects/own/sql-kai
pnpm install && pnpm build     # dist нужен для сборки (generate_context!)
cargo install --path src-tauri --features cli --bin sql-kai-cli
mv ~/.cargo/bin/sql-kai-cli ~/.cargo/bin/sql-kai   # команда — sql-kai
# переподписать стабильным сертификатом, чтобы vault trust не переспрашивал keychain:
codesign --force --sign "$(jq -r '.bundle.macOS.signingIdentity' src-tauri/tauri.conf.json)" ~/.cargo/bin/sql-kai

Другим пользователям (готовый бинарь из релиза)

Начиная с первого релиза после добавления CLI, release.sh кладёт sql-kai-cli-darwin-aarch64.tar.gz в assets GitLab-релиза:

curl -fL https://gitlab.com/kaidstor/sql-kai/-/releases/permalink/latest/downloads/sql-kai-cli-darwin-aarch64.tar.gz \
  | tar xz -C /usr/local/bin        # или ~/.local/bin, если он в PATH
sql-kai --version
Бинарь только для macOS arm64 (собирается локально на машине мейнтейнера). Intel-мак или Linux — собирать из исходников (раздел выше; понадобятся Rust, pnpm и системные зависимости Tauri). Скачивание через curl не ставит quarantine-атрибут; если файл скачан браузером — xattr -d com.apple.quarantine sql-kai.

У нового пользователя свой vault и пустой список профилей: sql-kai vault setup, затем sql-kai discover <ssh-alias> для каждого сервиса.

Запросы

Read-only по умолчанию

Каждая сессия сразу выполняет SET default_transaction_read_only = on. INSERT/UPDATE/DELETE/DDL упадут с ошибкой сервера — это защита от случайной записи в прод. Запись — явным флагом:

sql-kai domainator -c "UPDATE domains SET status='ok' WHERE id=42" --write

Транзакции

Несколько стейтментов (повторные -c, файл, stdin) уходят одним батчем — это одна неявная транзакция: ошибка в середине откатывает всё, сессия не остаётся в aborted-состоянии.

Форматы вывода

ФлагФормат
(без флага)pretty-таблица + (N rows); не-SELECT — -- N row(s) affected
--json{results:[{columns, rows, rowsAffected, truncated}], durationMs}; значения приведены к JSON-типам по реальным типам колонок: числа числами, bool как true/false, NULL = null, json/jsonb — объектами, остальное строками. Типы берутся честно (Parse каждого стейтмента, без выполнения), а не угадываются по виду значения: '3'::text останется строкой. Если тип не определился (редкость: стейтмент ссылается на объект, созданный/удалённый тем же батчем) — значения этого результата строками + предупреждение в stderr. Нужна точная строковая форма числа (огромный numeric, значимые нули) — кастуй в ::text
--csvCSV с заголовком (RFC 4180)
-t / --tuplesТолько значения через |, без заголовков — для grep/awk

Результат капится --max-rows N (по умолчанию 1000) — в выводе будет пометка truncated. -v печатает в stderr, куда именно подключились ([имя → user@host:port/db via ssh:… PostgreSQL 16.13 ro]).

Маскирование чувствительных колонок

Значения колонок, чьи имена похожи на креды (вхождение password/passwd/secret/ passphrase/credential, суффикс token/_key/apikey/_salt/_jwt, точное salt/jwt), во всех форматах вывода заменяются на [redacted] — вывод CLI оседает в логах агентских сессий, и SELECT * не должен туда ронять argon2-хэши и токены. NULL остаётся NULL. О факте маскирования sql-kai предупреждает в stderr; посмотреть реальные значения — флаг --no-redact:

sql-kai domainator -c "SELECT * FROM admins"              # password_hash → [redacted] (+ ⚠ в stderr)
sql-kai domainator -c "SELECT * FROM admins" --no-redact  # как есть
Маскирование работает в sql-kai q / sql-kai saved run. Вывод sql-kai exec (сырой psql через ssh) не маскируется.

Профили и discover

Профиль — это host/port/база/юзер + опциональный ssh-туннель; хранится в profiles.json (общий с GUI: заведённое в CLI сразу видно в приложении и наоборот).

sql-kai discover <ssh-alias> автоматизирует заведение профиля для типового rebrandy-сервиса (postgres в docker-compose на хосте):

  1. Идёт по ssh на хост (алиас из ~/.ssh/config.d/*, аутентификация ключами/agent).
  2. Находит postgres-контейнер в docker ps (имя с db/postgres; при необходимости sudo docker).
  3. Достаёт из env контейнера POSTGRES_USER / POSTGRES_DB / POSTGRES_PASSWORD.
  4. Выбирает точку подключения: опубликованный порт (docker port … 5432) → 127.0.0.1:порт, иначе IP контейнера в bridge-сети (с хоста маршрутизируется) → ip:5432.
  5. Сохраняет профиль (имя = алиас, ssh-туннель на алиас), пароль — в vault, и проверяет подключение.

Подключение потом идёт как в GUI: ssh -N -L локальный порт → точка из шага 4. Если контейнер пересоздали и IP «уехал» — просто повтори sql-kai discover. --dry-run покажет найденное без сохранения, --name задаст имя профиля.

Exec-режим (fallback)

sql-kai exec <ssh-alias> — прямой режим без профиля и vault, как у старого prod-db: ssh на хост → найти контейнер → docker exec psql. Пароль не нужен (psql внутри контейнера ходит по trust/peer). Вывод — сырой текст psql (-t, --csv прокидываются в psql). Тот же read-only guard: без --write в начало SQL добавляется SET default_transaction_read_only = on.

Когда нужен: до базы не достучаться туннелем (порт не публикуется и IP контейнера недоступен), пароля нет в env контейнера, или профиль заводить незачем. --dry-run печатает команду, не заходя на хост.

Интеграция с sec

sec — отдельный агент-безопасный менеджер секретов (значения не попадают в argv/историю/чат). sql-kai и sec не сливают хранилища: vault остаётся для GUI, sec — канал для CLI/агента и источник, где у пароля БД появляются аудит, версии и трекинг ротации. sql-kai зовёт sec из PATH (или KAI_SEC_BIN); ключ пароля по конвенции — <имя-профиля>/DB_PASSWORD.

Нужен свежий sec (с командами scan/meta). Если sql-kai ругается «sec в PATH устарел» — пересобери его (just install в каталоге sec, или go build -o ~/go/bin/sec .).

Пароль БД в sec вместо vault (прод-политика)

Для прод-баз пароль можно вообще не хранить в sql-kai, а держать только в sec — аудируемо и ротируемо:

sql-kai discover gidcaf --to-sec --no-vault    # пароль → sec (gidcaf/DB_PASSWORD), не в vault
sql-kai gidcaf -c "SELECT …" --from-sec        # берём пароль из sec на лету
# эквивалент без флага: sec run gidcaf -- sql-kai gidcaf -c "…" --password-env DB_PASSWORD

--to-sec кладёт найденный пароль в sec и проставляет meta --rotate-every 90d; --sec-key proj/KEY задаёт ключ явно. --from-sec (и --sec-key) на sql-kai <alias> / saved run берёт пароль из sec.

Ротация пароля роли

sql-kai rotate — то, чего не делает ни один инструмент в одиночку: sec генерирует/хранит/версионирует, sql-kai применяет в БД. sec здесь ещё и страховка от локаута — прежнее значение уходит в историю sec.

sql-kai rotate gidcaf --from-sec --yes    # роль по умолчанию = пользователь профиля

Порядок безопасный: сохранить новый пароль в sec (старое → история sec) → ALTER ROLE … PASSWORD → проверить свежим коннектом → только потом обновить vault. Если ALTER не прошёл — новый пароль ещё не в БД, откат: sec undo <key>. Флаги: --role, --sec-key, --length, --rotate-every, --yes.

Если ролью ходит сам сервис — после ротации он сломается, пока не обновишь его секрет (sec push → передеплой). sql-kai предупреждает и требует подтверждение (--yes в неинтерактиве).

Гигиена и проверка

  • История: sql-kai сам маскирует литералы после PASSWORD/IDENTIFIED BY при записи (… PASSWORD '***'), поэтому пароль не оседает в history.json. sql-kai history --scan дополнительно проверяет файл через sec scan (не осел ли где известный секрет).
  • Дрейф: sql-kai doctor по каждому профилю проверяет, что сохранённый пароль ещё аутентифицируется, и ловит расхождение «в vault одно, в sec другое, в БД работает третье». fail = хранимый пароль не подходит (ненулевой exit); sec stale подскажет, что пора крутить по срокам.

Переиспользование ssh (быстрее запросы)

Медленная часть подключения через ssh — не форвард, а рукопожатие и аутентификация ssh (~1–2 с). Каждый sql-kai — короткий процесс, поэтому без переиспользования каждый запрос платил бы за авторизацию заново.

Для профилей с ssh sql-kai держит персистентный ssh-мастер (OpenSSH ControlMaster): первый вызов проходит аутентификацию и оставляет фоновый мастер-коннект, последующие цепляют свой -L форвард к нему за ~один round-trip — без повторной авторизации. Мастер живёт в фоне и сам гаснет после простоя (ControlPersist, по умолчанию 5 мин).

1-й запрос:  ssh-auth (полная) ─► фоновый мастер (живёт ControlPersist)
                                     │
2-й, 3-й…:   форвард ── attach ──────┘   (без auth, ~1 RTT → БД)
  • Включено по умолчанию. --no-mux — разовый обычный туннель и всегда автономная сессия (мимо GUI/holder — их сессии mux-овые); KAI_SSH_MUX_TTL=<сек> — сколько мастер живёт после простоя.
  • Управляющие сокеты — в /tmp/kai-ssh-mux-<user>/ (0700), имя сокета = [user@]host:port.
  • sql-kai tunnel list — живые мастера; sql-kai tunnel close <host> или --all — закрыть (ssh -O exit).
  • Мастер поднимается best-effort: если не удался, форвард просто откатывается к обычному прямому соединению (медленнее, но работает).
  • GUI это не затрагивает — он и так держит один туннель на всю сессию.

Holder: сессии между запусками

Mux избавляет от повторной ssh-аутентификации, но каждый sql-kai — короткий процесс: он всё равно платил бы за pg-connect, а сессия (и открытая транзакция) умирала бы с ним. Поэтому запросы обслуживает сервер сессий:

sql-kai q ──► брокер GUI        (GUI запущен: сессию держит приложение)
      └─► holder            (иначе: фоновый `sql-kai holder run`, спавнится сам)
      └─► автономно         (--local / --no-mux / vault не разлочить тихо)

Holder — тот же broker-протокол, что у GUI, но фоновым процессом: pg-сессии и ssh-туннели живут между запусками sql-kai, повторные запросы идут в уже открытую сессию (быстрее даже mux-пути), а транзакция одного вызова доживает до следующего — BEGIN в одном sql-kai q, COMMIT в следующем.

  • Жизненный цикл: спавнится первым sql-kai q, только если vault разлочивается тихо (keychain-trust / KAI_VAULT_PASSWORD) — иначе sql-kai молча работает автономно. Сессии живут 15 мин простоя (с открытой транзакцией — 180 с: висящий BEGIN держит блокировки); сам holder гаснет через ~2 мин без сессий и обращений.
  • Погасить немедленно: sql-kai holder stop; vault lock в GUI и sql-kai vault revoke гасят его автоматически (DEK не должен переживать отзыв).
  • Обновление sql-kai: holder от прежней версии бинаря гасится и поднимается свежий (сверка версии при рукопожатии).
  • Безопасность: сокет holder.sock — 0600; DEK только в памяти процесса; KAI_VAULT_PASSWORD вычищается из окружения holder'а сразу после разлока — долгоживущий процесс не держит мастер-пароль и не передаёт его ssh-детям.
  • Мимо сервера сессий: --local — одноразовая автономная сессия; --no-mux — то же плюс свежий ssh без ControlMaster. Кастомные источники пароля (--password-env / --from-sec) всегда идут автономно.

Vault: как CLI читает пароли

Пароли БД и ssh-пассфразы лежат в vault.json, зашифрованные одним случайным ключом — DEK (AES-256-GCM). Сам DEK в открытом виде нигде не хранится: он «завёрнут» ключом, выведенным из мастер-пароля (Argon2id).

мастер-пароль ──Argon2id──► KEK ──расшифровывает──► DEK ──расшифровывает──► пароли (vault.json)

DEK можно получить тремя путями:
  1. мастер-пароль          — всегда работает (GUI и CLI)
  2. Touch ID (GUI)         — копия DEK в keychain, чтение гейтится биометрией
  3. cli trust (sql-kai)        — копия DEK в login keychain, чтение БЕЗ промпта

GUI спрашивает мастер-пароль один раз и держит DEK в памяти процесса до выхода. CLI-процесс живёт доли секунды — «держать в памяти» негде, и без trust каждый запуск требовал бы мастер-пароль. sql-kai vault trust решает это так:

  1. Разлочивает vault (спросит мастер-пароль — единственный интерактивный шаг).
  2. Кладёт копию DEK в login keychain macOS обычной записью (service com.kaidstor.sql-kai.vault, account dek-cli).
  3. Дальше каждый запуск sql-kai молча читает эту запись: macOS разрешает читать keychain-запись без подтверждения тому бинарю, который её создал (ACL по подписи кода). Любому другому приложению система покажет диалог.

Что это значит с точки зрения безопасности:

  • На диске копия DEK защищена шифрованием login keychain — он расшифровывается паролем пользователя при входе в macOS.
  • Пока сессия пользователя разблокирована, sql-kai читает пароли без вопросов — тот же trade-off, что у ssh-agent с добавленным ключом.
  • Touch ID-копия GUI — отдельная запись: её чтение приложение дополнительно гейтит биометрией. Для CLI биометрию не ставим сознательно: агент, шлющий десяток запросов, дёргал бы палец на каждый.
  • sql-kai vault revoke удаляет запись — остаётся путь через мастер-пароль.
  • Если vault пересоздали, старая копия DEK перестаёт подходить (GCM-аутентификация падает) — sql-kai сам удалит протухшую запись и попросит сделать trust заново.

Разлок без trust (скрипты, CI)

Полная цепочка, которую sql-kai пробует по порядку, когда профилю нужен секрет из vault:

  1. keychain-trust (тихо);
  2. env KAI_VAULT_PASSWORD — мастер-пароль из окружения;
  3. интерактивный запрос в терминале (если есть TTY).

Полный обход vault — --password-env VAR: пароль БД берётся из указанной env-переменной, vault не трогается вовсе.

Troubleshooting

СимптомЧто делать
Системный диалог «sql-kai wants to access …» после обновления бинаря Подпись бинаря сменилась, keychain перепроверяет ACL — «Always Allow» один раз, либо заново sql-kai vault trust. Релизный бинарь подписывается стабильным сертификатом, у него таких промптов нет.
the CLI trust key was stale and has been reset Vault был пересоздан — sql-kai vault trust заново.
vault заблокирован… в скрипте без TTY sql-kai vault trust (один раз интерактивно), либо KAI_VAULT_PASSWORD, либо --password-env.
discover: «нет ни опубликованного порта, ни IP» / подключение по туннелю не проходит Использовать sql-kai exec <alias> — работает через docker exec без открытых портов.
cannot execute … in a read-only transaction Так и задумано: добавь --write, если запись действительно согласована.
Внешний managed-Postgres (не в docker на хосте) discover его не найдёт — завести профиль руками в GUI (или найти DSN в .env/Infisical).
ssh-мастер держит коннект к хосту после работы Это ожидаемо — он гаснет сам после простоя (KAI_SSH_MUX_TTL, 5 мин). Закрыть сразу: sql-kai tunnel close --all; разовый запрос без мастера — --no-mux.
Фоновый процесс sql-kai holder run после запросов Это держатель сессий (см. «Holder») — гаснет сам через ~2 мин после закрытия сессий; немедленно — sql-kai holder stop. Не поднимать вовсе — --local / --no-mux.
