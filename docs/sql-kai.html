sql-kai — CLI к sql-kai

Консольный клиент поверх того же Rust-ядра, что и приложение sql-kai: общие профили подключений, ssh-туннели, vault с паролями и история запросов. Собирается из этого же репозитория (src-tauri, cargo-фича cli).

Быстрый старт

sql-kai profiles list [фильтр]              # профили (общие с GUI); фильтр — подстрока
                                            # по name/group/host/db/ssh: profiles list vuln
sql-kai domainator -c "SELECT count(*) FROM domains"
echo "SELECT now()" | sql-kai orchestrator  # SQL со stdin; или -f query.sql
sql-kai coordinator -c "..." --json         # структурный вывод: числа/bool/null/json типизированы
sql-kai tables coordinator --counts         # таблицы + примерное число строк

sql-kai <alias> … — сокращение для sql-kai q <alias> …. alias — имя, id или группа профиля.

Установка

С этой машины (из репозитория)

cd ~/Projects/own/sql-kai
pnpm install && pnpm build     # dist нужен для сборки (generate_context!)
cargo install --path src-tauri --features cli --bin sql-kai-cli
mv ~/.cargo/bin/sql-kai-cli ~/.cargo/bin/sql-kai   # команда — sql-kai
# переподписать стабильным сертификатом, чтобы vault trust не переспрашивал keychain:
codesign --force --sign "$(jq -r '.bundle.macOS.signingIdentity' src-tauri/tauri.conf.json)" ~/.cargo/bin/sql-kai

Другим пользователям (готовый бинарь из релиза)

Начиная с первого релиза после добавления CLI, release.sh кладёт sql-kai-cli-darwin-aarch64.tar.gz в assets GitHub-релиза:

curl -fL https://github.com/Kaidstor/sql-kai/releases/latest/download/sql-kai-cli-darwin-aarch64.tar.gz \
  | tar xz -C /usr/local/bin        # или ~/.local/bin, если он в PATH
sql-kai --version
Бинарь только для macOS arm64 (собирается локально на машине мейнтейнера). Intel-мак или Linux — собирать из исходников (раздел выше; понадобятся Rust, pnpm и системные зависимости Tauri). Скачивание через curl не ставит quarantine-атрибут; если файл скачан браузером — xattr -d com.apple.quarantine sql-kai.

У нового пользователя свой vault и пустой список профилей: sql-kai vault setup, затем sql-kai discover <ssh-alias> для каждого сервиса.

Первый запуск: sql-kai init

Одна интерактивная команда вместо четырёх ручных шагов. Каждый шаг спрашивает отдельно и показывает, что именно сделает; отказ от шага не мешает остальным:

sql-kai init                       # [1/4] … [4/4], всё с подтверждением
sql-kai init --skip-if-configured  # для установщиков: молча выйти, если всё уже настроено
  1. Команда sql-kai в PATH — симлинк на CLI внутри бандла (--bin-dir, по умолчанию ~/.local/bin): так CLI обновляется вместе с приложением. Если каталог не в PATH, init печатает строку для ~/.zshrc. Запуск не из бандла (cargo install) — шаг пропускается.
  2. vault trust — тихий доступ к паролям (см. «Vault»).
  3. MCP — sql-kai mcp install для AI-агента (см. «MCP»).
  4. Автодополнение — скрипт для шелла (--shell zsh|bash|fish, по умолчанию из $SHELL) в стандартный каталог + строка подключения в rc-файл.
Без TTY init ничего не меняет — печатает список ручных команд, которые сделали бы то же самое. Это безопасно звать из скриптов.

Отдельно скрипт автодополнения — sql-kai completion zsh|bash|fish. Кроме подкоманд и флагов он дополняет имена профилей и групп: сгенерированный скрипт для этого зовёт sql-kai completion --profiles (руками эта форма не нужна).

Запросы

Параметры запроса

Запрос с $1..$N приложение не отправляет как есть — перед запуском открывается окно со значениями (по полю на каждый плейсхолдер) и кнопкой Run; то же для Explain. Значения экранируются как литералы и подставляются на бэкенде, поэтому кавычки и апострофы в данных запрос не ломают.

Введённые значения запоминаются в vault — зашифрованными тем же ключом, что и пароли БД, — и в следующий раз окно открывается уже заполненным. В history.json они не попадают: там у запроса остаются $1, и это не мелочь — параметр ровно то место, куда попадает токен (UPDATE … SET api_token = $1). Кнопка «Forget saved» стирает запомненное для этого запроса; при запертом vault окно просто открывается пустым. $1 внутри строки, комментария или $tag$…$tag$ — текст, значения для него не спрашиваются.

Read-only по умолчанию

Каждый читающий батч выполняется внутри явной транзакции BEGIN READ ONLY (SET default_transaction_read_only = on остаётся вторым слоем — сам по себе он границей не является, это USERSET-настройка, которую батч снял бы первой же строкой). INSERT/UPDATE/DELETE/DDL упадут с ошибкой сервера — это защита от случайной записи в прод. Всё, что вывело бы батч из этого блока или сняло бы с него read-only (COMMIT, ROLLBACK, DISCARD, SET TRANSACTION, SET …transaction_read_only и его функциональная форма set_config(…)), отвергается до отправки в базу; отдельно отвергается запись мимо базы — COPY … TO PROGRAM, COPY … TO '/путь', lo_export. Запись — явным флагом:

sql-kai domainator -c "UPDATE domains SET status='ok' WHERE id=42" --write

Запись в production

Профилю с меткой production (красный бейдж PROD в GUI) одного --write мало: запись дополнительно требует разрешения от человека. Способы — любой на выбор:

СпособКогда
Ввести имя профиля в ответ на вопросЗапуск в терминале: sql-kai сам спросит перед подключением
--prod-write (рядом с --write)Осознанная разовая команда: разрешение видно в самой команде — и в истории shell, и агенту, который просит её подтвердить
SQL_KAI_ALLOW_PROD_WRITE=<профиль>Неинтерактивные сценарии: MCP, CI, пайп. Значение — имя/id профиля (можно список через запятую) или 1 для всех prod-профилей

Без TTY (MCP, пайп, CI) вопрос задавать некому, поэтому вариант остаётся один — env: по умолчанию запись в прод оттуда не проходит. Для MCP это принципиально: переменную задаёт пользователь в конфиге своего клиента (env сервера sql-kai), модель себе её не выставит, а "write": true в аргументах tool'а сам по себе прод не открывает. Барьер общий для всех путей записи — q, saved run, rotate, MCP-tool query и exec на ssh-хост, к которому привязан prod-профиль. Сессии живут в сервере сессий (GUI или holder), и он держит свою проверку: запрос без пройденного барьера в prod-профиль не пишет, даже если пришёл в сокет мимо sql-kai — например от старой версии CLI. Каждая прод-запись попадает в журнал брокера. Чтение из прод-профилей ничего не спрашивает.

Транзакции

Несколько стейтментов (повторные -c, файл, stdin) уходят одним батчем — это одна неявная транзакция: ошибка в середине откатывает всё, сессия не остаётся в aborted-состоянии.

Форматы вывода

Маскирование чувствительных колонок

Значения колонок, чьи имена похожи на креды (вхождение password/passwd/secret/ passphrase/credential, суффикс token/_key/apikey/_salt/_jwt, точное salt/jwt), во всех форматах вывода заменяются на [redacted] — вывод CLI оседает в логах агентских сессий, и SELECT * не должен туда ронять argon2-хэши и токены. NULL остаётся NULL. О факте маскирования sql-kai предупреждает в stderr; посмотреть реальные значения — флаг --no-redact:

sql-kai domainator -c "SELECT * FROM admins"              # password_hash → [redacted] (+ ⚠ в stderr)
sql-kai domainator -c "SELECT * FROM admins" --no-redact  # как есть
Маскирование работает в sql-kai q / sql-kai saved run. Вывод sql-kai exec (сырой psql через ssh) не маскируется.

Схема базы одним дампом

sql-kai schema <alias> отдаёт всю структуру базы за один поход в каталог: таблицы (обычные, партиционированные, foreign), вьюхи и матвьюхи — с колонками, типами, nullability, дефолтами, identity/generated (stored или virtual), констрейнтами, индексами, триггерами, RLS-политиками и границами партиций, плюс enum-типы, домены, composite-типы, standalone-секвенции, функции и процедуры. Нужен PostgreSQL 12+ (дамп читает attgenerated); на более старом сервере команда отказывает и отсылает к точечным tables/columns/indexes/ddl. Это замена обхода tables → columns/ddl/indexes по каждой таблице: вместо десятков round-trip — константное число каталожных запросов, отправленных одним батчем, то есть ещё и один согласованный снимок.

-- база: domainator   сервер: 16.4
-- скрыто: системные схемы, объекты расширений, партиции (--internal); тела вьюх и функций (--definitions); комментарии (--comments)

== схема public ==

table public.domains
  id          bigint        not null  identity always
  name        text          not null
  status      domain_state  not null  default 'new'::domain_state
  created_at  timestamptz   not null  default now()
  constraint domains_pkey PRIMARY KEY (id)
  constraint domains_name_key UNIQUE (name)
  index domains_pkey unique USING btree (id)
  index domains_status_idx USING btree (status)
  trigger set_updated_at BEFORE UPDATE -> touch_updated_at()

enum public.domain_state = new | ok | failed

-- итого: схем 1, таблиц 1, enum 1
ФлагЧто делает
--schema <name>Только одна схема (можно и системную, например pg_catalog)
--definitionsТела вьюх и исходники функций
--commentsТексты COMMENT ON: таблиц, колонок, типов, функций
--internalПоказать скрытое по умолчанию: системные схемы, объекты расширений (postgis, pg_trgm, timescaledb) и листовые партиции — у родителя вместо них стоит (партиций: N)
--jsonДерево схем вместо текста (--csv/-t здесь не бывает: это не таблица)

Шапка дампа сама перечисляет, что скрыто, — по ней видно, какой флаг добавить. Итоговая строка считает только непустые категории.

Каталожные запросы используют attgenerated (generated-колонки), поэтому нужен PostgreSQL 12+; на 10/11 упадёт весь дамп целиком. Тот же дамп доступен агенту как MCP-tool schema (см. «MCP»).

Профили и discover

Профиль — это host/port/база/юзер + опциональный ssh-туннель; хранится в profiles.json (общий с GUI: заведённое в CLI сразу видно в приложении и наоборот).

sql-kai discover <ssh-alias> автоматизирует заведение профиля для типового rebrandy-сервиса (postgres в docker-compose на хосте):

  1. Идёт по ssh на хост (алиас из ~/.ssh/config.d/*, аутентификация ключами/agent).
  2. Находит postgres-контейнер в docker ps (имя с db/postgres; при необходимости sudo docker).
  3. Достаёт из env контейнера POSTGRES_USER / POSTGRES_DB / POSTGRES_PASSWORD.
  4. Выбирает точку подключения: опубликованный порт (docker port … 5432) → 127.0.0.1:порт, иначе IP контейнера в bridge-сети (с хоста маршрутизируется) → ip:5432.
  5. Сохраняет профиль (имя = алиас, ssh-туннель на алиас), пароль — в vault, и проверяет подключение.

Подключение потом идёт как в GUI: ssh -N -L локальный порт → точка из шага 4. Если контейнер пересоздали и IP «уехал» — просто повтори sql-kai discover. --dry-run покажет найденное без сохранения, --name задаст имя профиля.

Exec-режим (fallback)

sql-kai exec <ssh-alias> — прямой режим без профиля и vault, как у старого prod-db: ssh на хост → найти контейнер → docker exec psql. Пароль не нужен (psql внутри контейнера ходит по trust/peer). Вывод — сырой текст psql (-t, --csv прокидываются в psql). Тот же read-only guard, но границей служит транзакция: без --write батч уходит в psql с --single-transaction и первым же SET TRANSACTION READ ONLY — внутри такого блока Postgres не даёт ни писать, ни снять с себя read-only. Выйти из него тоже нельзя: и транзакционные команды (COMMIT, ROLLBACK, DISCARD, SET TRANSACTION), и мета-команды psql, уводящие из транзакции или тащащие чужой SQL (\c, \i, \gexec, \o, \copy, \!), на чтении отвергаются; describe и переключатели вывода (\d…, \l, \x, \timing) проходят.

Здесь же отвергается и запись мимо базы: COPY … TO PROGRAM запускает шелл на сервере, COPY … TO '/путь' и lo_export пишут его диск, а read-only транзакция не покрывает ни то, ни другое (Postgres проверяет только запись в базу). На exec-пути это особенно важно: psql внутри контейнера работает под POSTGRES_USER, как правило суперюзером. Выгрузка данных — через COPY … TO STDOUT.

Когда нужен: до базы не достучаться туннелем (порт не публикуется и IP контейнера недоступен), пароля нет в env контейнера, или профиль заводить незачем. --dry-run печатает команду, не заходя на хост.

Журнал postgres-сервера

sql-kai logs <alias> — ssh на хост профиля → docker logs его контейнера. Профиль из discover уже знает и ssh-хост, и контейнер, поэтому ответ на «почему запрос упал / что там происходит» достаётся без ручного похода на сервер. Главное: в отличие от pg_stat_*, это работает, когда postgres соединения уже не принимает — упал, перезапускается по кругу, забил диск.

sql-kai logs vuln                      # последние 500 строк
sql-kai logs vuln -n 100 --since 10m   # хвост за последние 10 минут
sql-kai logs vuln -f                   # стримить до Ctrl+C
sql-kai logs vuln | grep -i error      # postgres пишет в stderr, но sql-kai сливает его в stdout
sql-kai logs vuln --dry-run            # показать команду, не заходя на хост
ФлагЧто делает

Локальный профиль (127.0.0.1) читается без ssh — тот же docker logs на этой машине. Профиль, который ходит в базу напрямую и без ssh (managed-Postgres), команда честно отвергает: журнала там взять неоткуда, он в панели провайдера.

Форк базы: миграции не на проде

sql-kai fork <alias> [новое-имя] поднимает копию базы профиля в локальном docker и заводит на неё профиль: песочница, где можно применять миграции, ронять таблицы и мерить время рерайта, ничем не рискуя.

sql-kai fork vuln --dry-run     # план: источник, объём дампа, образ, порт, имя профиля
sql-kai fork vuln               # только схема (быстро)
sql-kai fork vuln --data        # вместе с данными (дамп может быть на гигабайты)
sql-kai vuln-fork -f migration.sql --write   # прогон миграции на копии
docker rm -f sql-kai-fork-vuln-fork          # снести форк
  1. Подключение к источнику — обычной read-only-сессией sql-kai (vault/sec, ssh-туннель).
  2. pg_dump — через ssh + docker exec на хосте источника либо локальным pg_dump, если ssh не нужен. С --data дамп держит ACCESS SHARE-локи: обычные запросы не мешает, а вот DDL и VACUUM FULL на источнике подождут.
  3. docker run postgres:<мажор версии источника> (--image — задать свой) на 127.0.0.1, порт свободный или --port.
  4. Заливка дампа и профиль <alias>-fork (или имя из аргумента/--name), пароль — в vault.

Флаги: --replace (снести прежний контейнер форка и создать заново), --yes (без подтверждения), --container (контейнер источника, когда их несколько), --password-env / --from-sec / --sec-key (откуда взять пароль источника).

Форк не наследует метку production — на нём запись не переспрашивает. Контейнер называется sql-kai-fork-<имя-профиля> и живёт, пока его не снесут: docker rm -f. Копия без данных проверяет синтаксис и совместимость схемы; чтобы оценить время рерайта и увидеть реальные планы, нужен --data.
Где оказываются данные. Форк всегда локальный — прод участвует только как источник дампа, на удалённой стороне ничего не создаётся (единственная операция над источником — pg_dump: SELECT-ы и ACCESS SHARE-локи). Обратная сторона: с --data боевые данные переезжают на вашу машину, поэтому с профиля, помеченного production, такой форк требует отдельного подтверждения — имя профиля в терминале, флаг --prod-data или SQL_KAI_ALLOW_PROD_DUMP=<профиль>; --yes его не снимает. Дамп пишется в $TMPDIR файлом с правами 0600 и удаляется после заливки — но сознательно остаётся, если psql дамп не залил (иначе нечего разбирать), и путь печатается. Сама копия лежит в docker-томе без шифрования и живёт до docker rm -f. Порт контейнера слушает только 127.0.0.1, пароль форка случайный и передаётся через env, а не через argv. Если форкаете базу с ПДн — сносите копию сразу после проверки миграции.

MCP: sql-kai как инструмент агента

sql-kai mcp [<alias>] — MCP-сервер поверх stdio (newline-delimited JSON-RPC на stdout, диагностика в stderr). Запросы идут через тот же сервер сессий, что и обычный CLI: vault уже разблокирован, туннели подняты, сессия по умолчанию read-only.

sql-kai mcp <alias>

У каждого tool'а объявлены annotations (readOnlyHint, destructiveHint, …) и outputSchema: ответ приходит и текстом (content), и разобранным деревом (structuredContent).

Ответ ограничен и по строкам, и по объёму: maxRows клампится до 10000, на данные отводится 256 KiB, на одну ячейку — 16 KiB. Обрезка не молчаливая: в structuredContent приходят truncated и truncated_by_size, длинная ячейка получает пометку о том, сколько байт срезано. Так широкая таблица или многомегабайтный jsonb не уносят контекст модели целиком.

Долгий запрос больше не затыкает сервер: tools/call выполняется параллельно (до 4 одновременно), ping и tools/list отвечают, пока он идёт. Отмены отдельного вызова нет — cancel у сервера сессий адресуется профилю и погасил бы соседний запрос к той же базе.

Запись в production через MCP не проходит по умолчанию. У сервера нет TTY (stdin занят протоколом), спросить человека невозможно, поэтому "write": true для профиля с меткой production разрешает только SQL_KAI_ALLOW_PROD_WRITE в окружении самого сервера — то есть в конфиге MCP-клиента, куда модель не пишет. См. «Запись в production».

sql-kai mcp install claude-code         # прописать сервер по всем профилям
sql-kai mcp install cursor --profile vuln --dry-run   # закрепить за одной базой, только показать

Конфиги пользовательские, не проектные: сервер ставится один раз на все проекты. Слияние аккуратное — чужие серверы и любые прочие ключи файла сохраняются, перед записью делается .bak (--no-backup отключает), запись атомарная и проверяется перечитыванием. Команда в записи — путь к текущему бинарю (--command переопределяет), имя записи — sql-kai (--name); существующую запись с тем же именем перезаписывает только --force. --profile <alias> проверяет алиас сразу, чтобы опечатка не всплыла при первом запросе агента.

Разрешить агенту запись в конкретную прод-базу можно только вручную — дописав в ту же запись конфига "env": {"SQL_KAI_ALLOW_PROD_WRITE": "<профиль>"}. mcp install этого не делает и никогда не предложит.

Интеграция с sec

sec — отдельный агент-безопасный менеджер секретов (значения не попадают в argv/историю/чат). sql-kai и sec не сливают хранилища: vault остаётся для GUI, sec — канал для CLI/агента и источник, где у пароля БД появляются аудит, версии и трекинг ротации. sql-kai зовёт sec из PATH (или SQL_KAI_SEC_BIN); ключ пароля по конвенции — <имя-профиля>/DB_PASSWORD.

Нужен свежий sec (с командами scan/meta). Если sql-kai ругается «sec в PATH устарел» — пересобери его (just install в каталоге sec, или go build -o ~/go/bin/sec .).

Пароль БД в sec вместо vault (прод-политика)

Для прод-баз пароль можно вообще не хранить в sql-kai, а держать только в sec — аудируемо и ротируемо:

sql-kai discover gidcaf --to-sec --no-vault    # пароль → sec (gidcaf/DB_PASSWORD), не в vault
sql-kai gidcaf -c "SELECT …" --from-sec        # берём пароль из sec на лету
# эквивалент без флага: sec run gidcaf -- sql-kai gidcaf -c "…" --password-env DB_PASSWORD

--to-sec кладёт найденный пароль в sec и проставляет meta --rotate-every 90d; --sec-key proj/KEY задаёт ключ явно. --from-sec (и --sec-key) на sql-kai <alias> / saved run берёт пароль из sec.

Ротация пароля роли

sql-kai rotate — то, чего не делает ни один инструмент в одиночку: sec генерирует/хранит/версионирует, sql-kai применяет в БД. sec здесь ещё и страховка от локаута — прежнее значение уходит в историю sec.

sql-kai rotate gidcaf --from-sec --yes    # роль по умолчанию = пользователь профиля

Порядок безопасный: сохранить новый пароль в sec (старое → история sec) → ALTER ROLE … PASSWORD → проверить свежим коннектом → только потом обновить vault. Если ALTER не прошёл — новый пароль ещё не в БД, откат: sec undo <key>. Флаги: --role, --sec-key, --length, --rotate-every, --yes.

Если ролью ходит сам сервис — после ротации он сломается, пока не обновишь его секрет (sec push → передеплой). sql-kai предупреждает и требует подтверждение (--yes в неинтерактиве).

Гигиена и проверка

  • История: sql-kai сам маскирует литералы после PASSWORD/IDENTIFIED BY при записи (… PASSWORD '***'), поэтому пароль не оседает в history.json. sql-kai history --scan дополнительно проверяет файл через sec scan (не осел ли где известный секрет).
  • Дрейф: sql-kai doctor по каждому профилю проверяет, что сохранённый пароль ещё аутентифицируется, и ловит расхождение «в vault одно, в sec другое, в БД работает третье». fail = хранимый пароль не подходит (ненулевой exit); sec stale подскажет, что пора крутить по срокам.

Переиспользование ssh (быстрее запросы)

Медленная часть подключения через ssh — не форвард, а рукопожатие и аутентификация ssh (~1–2 с). Каждый sql-kai — короткий процесс, поэтому без переиспользования каждый запрос платил бы за авторизацию заново.

Для профилей с ssh sql-kai держит персистентный ssh-мастер (OpenSSH ControlMaster): первый вызов проходит аутентификацию и оставляет фоновый мастер-коннект, последующие цепляют свой -L форвард к нему за ~один round-trip — без повторной авторизации. Мастер живёт в фоне и сам гаснет после простоя (ControlPersist, по умолчанию 5 мин).

1-й запрос:  ssh-auth (полная) ─► фоновый мастер (живёт ControlPersist)
                                     │
2-й, 3-й…:   форвард ── attach ──────┘   (без auth, ~1 RTT → БД)
  • Включено по умолчанию. --no-mux — разовый обычный туннель и всегда автономная сессия (мимо GUI/holder — их сессии mux-овые); SQL_KAI_SSH_MUX_TTL=<сек> — сколько мастер живёт после простоя.
  • Управляющие сокеты — в /tmp/kai-ssh-mux-<user>/ (0700), имя сокета = [user@]host:port.
  • sql-kai tunnel list — живые мастера; sql-kai tunnel close <host> или --all — закрыть (ssh -O exit).
  • Мастер поднимается best-effort: если не удался, форвард просто откатывается к обычному прямому соединению (медленнее, но работает).
  • GUI это не затрагивает — он и так держит один туннель на всю сессию.

Holder: сессии между запусками

Mux избавляет от повторной ssh-аутентификации, но каждый sql-kai — короткий процесс: он всё равно платил бы за pg-connect, а сессия (и открытая транзакция) умирала бы с ним. Поэтому запросы обслуживает сервер сессий:

sql-kai q ──► брокер GUI        (GUI запущен: сессию держит приложение)
      └─► holder            (иначе: фоновый `sql-kai holder run`, спавнится сам)
      └─► автономно         (--local / --no-mux / vault не разлочить тихо)

Holder — тот же broker-протокол, что у GUI, но фоновым процессом: pg-сессии и ssh-туннели живут между запусками sql-kai, повторные запросы идут в уже открытую сессию (быстрее даже mux-пути), а транзакция одного вызова доживает до следующего — BEGIN в одном sql-kai q, COMMIT в следующем.

  • Жизненный цикл: спавнится первым sql-kai q, только если vault разлочивается тихо (keychain-trust / SQL_KAI_VAULT_PASSWORD) — иначе sql-kai молча работает автономно. Сессии живут 15 мин простоя (с открытой транзакцией — 180 с: висящий BEGIN держит блокировки); сам holder гаснет через ~2 мин без сессий и обращений.
  • Погасить немедленно: sql-kai holder stop; vault lock в GUI и sql-kai vault revoke гасят его автоматически (DEK не должен переживать отзыв).
  • Обновление sql-kai: holder от прежней версии бинаря гасится и поднимается свежий (сверка версии при рукопожатии).
  • Безопасность: сокет holder.sock — 0600; DEK только в памяти процесса; SQL_KAI_VAULT_PASSWORD вычищается из окружения holder'а сразу после разлока — долгоживущий процесс не держит мастер-пароль и не передаёт его ssh-детям.
  • Мимо сервера сессий: --local — одноразовая автономная сессия; --no-mux — то же плюс свежий ssh без ControlMaster. Кастомные источники пароля (--password-env / --from-sec) всегда идут автономно.

Vault: как CLI читает пароли

Пароли БД и ssh-пассфразы лежат в vault.json, зашифрованные одним случайным ключом — DEK (AES-256-GCM). Сам DEK в открытом виде нигде не хранится: он «завёрнут» ключом, выведенным из мастер-пароля (Argon2id).

мастер-пароль ──Argon2id──► KEK ──расшифровывает──► DEK ──расшифровывает──► пароли (vault.json)

DEK можно получить тремя путями:
  1. мастер-пароль          — всегда работает (GUI и CLI)
  2. Touch ID (GUI)         — копия DEK в keychain, чтение гейтится биометрией
  3. cli trust (sql-kai)        — копия DEK в login keychain, чтение БЕЗ промпта

GUI спрашивает мастер-пароль один раз и держит DEK в памяти процесса до выхода. CLI-процесс живёт доли секунды — «держать в памяти» негде, и без trust каждый запуск требовал бы мастер-пароль. sql-kai vault trust решает это так:

  1. Разлочивает vault (спросит мастер-пароль — единственный интерактивный шаг).
  2. Кладёт копию DEK в login keychain macOS обычной записью (service com.kaidstor.sql-kai.vault, account dek-cli).
  3. Дальше каждый запуск sql-kai молча читает эту запись: macOS разрешает читать keychain-запись без подтверждения тому бинарю, который её создал (ACL по подписи кода). Любому другому приложению система покажет диалог.

Что это значит с точки зрения безопасности:

  • На диске копия DEK защищена шифрованием login keychain — он расшифровывается паролем пользователя при входе в macOS.
  • Пока сессия пользователя разблокирована, sql-kai читает пароли без вопросов — тот же trade-off, что у ssh-agent с добавленным ключом.
  • Touch ID-копия GUI — отдельная запись: её чтение приложение дополнительно гейтит биометрией. Для CLI биометрию не ставим сознательно: агент, шлющий десяток запросов, дёргал бы палец на каждый.
  • sql-kai vault revoke удаляет запись — остаётся путь через мастер-пароль.
  • Если vault пересоздали, старая копия DEK перестаёт подходить (GCM-аутентификация падает) — sql-kai сам удалит протухшую запись и попросит сделать trust заново.

Разлок без trust (скрипты, CI)

Полная цепочка, которую sql-kai пробует по порядку, когда профилю нужен секрет из vault:

  1. keychain-trust (тихо);
  2. env SQL_KAI_VAULT_PASSWORD — мастер-пароль из окружения;
  3. интерактивный запрос в терминале (если есть TTY).

Полный обход vault — --password-env VAR: пароль БД берётся из указанной env-переменной, vault не трогается вовсе.

запись в production-профиль … заблокирована Одного --write для прода мало. В терминале — подтвердить именем профиля, иначе --prod-write; из MCP/CI/пайпа — только SQL_KAI_ALLOW_PROD_WRITE в окружении процесса (см. «Запись в production»).
CREATE INDEX CONCURRENTLY cannot run inside a transaction block Несколько стейтментов (повторные -c, ;, файл) уходят одним батчем — это транзакция. CONCURRENTLY (и VACUUM) нужно звать отдельной командой с одним стейтментом.
sql-kai schema: ошибка про attgenerated Дамп требует PostgreSQL 12+; на 10/11 падает весь батч. Для старого сервера — tables/columns/ddl.
sql-kai logs: «контейнер нашёлся, но не определилась база» psql внутри контейнера уже не отвечает — sql-kai печатает готовую команду в обход (ssh <host> docker logs --tail N <контейнер>). «Контейнер не опознан» — задать явно: --container <имя>.
mcp install claude-code переписал весь ~/.claude.json Файл перечитывается и пишется целиком, поэтому форматирование меняется; содержимое сохраняется, рядом остаётся .bak. Конфиг с комментариями (JSONC) sql-kai не трогает вовсе — скажет дописать запись руками.
Внешний managed-Postgres (не в docker на хосте) discover его не найдёт — завести профиль руками в GUI (или найти DSN в .env/Infisical).
ssh-мастер держит коннект к хосту после работы Это ожидаемо — он гаснет сам после простоя (SQL_KAI_SSH_MUX_TTL, 5 мин). Закрыть сразу: sql-kai tunnel close --all; разовый запрос без мастера — --no-mux.
Фоновый процесс sql-kai holder run после запросов Это держатель сессий (см. «Holder») — гаснет сам через ~2 мин после закрытия сессий; немедленно — sql-kai holder stop. Не поднимать вовсе — --local / --no-mux.
