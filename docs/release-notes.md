# Заметки релиза — как это делают Zed и Warp

Справочная заметка: откуда берётся текст, который пользователь видит в диалоге
«Что нового» и на странице релиза, и какие есть более взрослые схемы, если наша
перестанет устраивать. Ничего из описанного здесь менять прямо сейчас не нужно —
решение по итогам разбора см. в конце.

## Как устроено у нас

Генерация — в общем скрипте личных проектов `../_release/tauri-release.sh`
(секция `--- changelog ---`, вне этого репозитория; его же использует tcp-kai):

1. `NOTES="…" ./release.sh` — свой текст, если задан;
2. иначе `git log "$PREV_TAG..HEAD" --pretty='- %s'` с отфильтрованными
   `release:`-коммитами;
3. если пусто — `Release $TAG`.

Результат уезжает в двух местах: в `description` GitLab-релиза и в поле `notes`
файла `latest.json`, который читает апдейтер.

Потребление — в приложении:

- `src/lib/whatsNew.ts` тянет последние релизы через публичный GitLab API
  (`/api/v4/projects/kaidstor%2Fsql-kai/releases`) и показывает их `description`
  в диалоге «Что нового» после обновления;
- офлайн-фолбэк — `notes` из `latest.json`, которые апдейтер складывает в
  localStorage перед перезапуском (`stashPendingNotes`).

Схема держится на том, что коммиты пишутся через скилл `/gcm` — Conventional
Commits по-русски, поэтому сабжект коммита сам по себе читаем и годится в
заметки почти без правки.

## Zed — заметка живёт рядом с изменением

Текст пишет автор изменения, в описании PR, после маркера из шаблона:

```
Release Notes:
- Added/Fixed/Improved ...
```

Правила из их доков:

- строка пишется, только если пользователь может увидеть или почувствовать
  разницу; иначе `Release Notes: N/A` — и скрипт пропускает такой PR целиком
  (правки доков — всегда `N/A`);
- формулировка — на языке пользователя редактора, без внутреннего жаргона;
- если изменение добавляет настройку или кейбинд — назвать их прямо в заметке,
  не заставляя лезть в доки;
- технические детали для команды — **выше** маркера, они в релиз не попадут;
- откат уже вышедшей фичи описывается отдельной строкой; откат невышедшей —
  заменой заметки исходного PR на `N/A`.

По средам скрипт `get-preview-channel-changes` собирает всё, что ниже маркера, у
смерженных PR (плюс ссылка на PR и автор, если он не из команды) — это и
становится release notes канала preview.

Главная идея: **заметка пишется в момент изменения, пока контекст свежий**, а на
релизе остаётся только сборка — сочинять текст задним числом не приходится.

## Warp — курируемый changelog

Противоположный полюс: changelog как редактируемый человеком документ. Релизы
примерно раз в неделю (четверг), запись — `YYYY.MM.DD (vX.X.X…)`, внутри
фиксированные секции **New features / Improvements / Bug fixes**. Формулировки
пользовательские («Added a connection indicator for cloud agent sessions», а не
сабжект коммита), у пунктов — ссылки на PR и кредиты контрибьюторам.
Публикуется как страница доков с `.md`-экспортом.

## Что из этого применимо здесь

PR-ов в проекте нет — коммиты идут прямо в `main`, поэтому zed-овский маркер
естественно переезжает в git-трейлер коммита. Это же конвенция нативного GitLab
Changelog API (он отбирает коммиты по трейлеру `Changelog:` и раскладывает по
категориям из `.gitlab/changelog_config.yml`), так что «как в Zed» и
«forge-native» здесь совпали бы:

```
feat(shortcuts): ⌘⇧W — закрыть активное соединение

<тело: почему и как — для себя-будущего>

Changelog: added
Release-Note: ⌘⇧W закрывает активное соединение целиком — вместе с пунктом
  меню File → Close Connection. ⌘K ⌘W по-прежнему закрывает только вкладки.
```

Сборка на релизе — локально, без API:

```bash
git log "$PREV_TAG..HEAD" \
  --format='%(trailers:key=Release-Note,valueonly)%x00%(trailers:key=Changelog,valueonly)'
```

с группировкой по значению `Changelog:` в warp-овские секции и фолбэк-цепочкой
`NOTES` → трейлеры → сабжекты коммитов (как сейчас). Что это дало бы: ручной шаг
на релизе исчезает совсем, коммиты без трейлера (рефакторинг, правки скиллов,
`release:`) в заметки не попадают сами, текст сразу пользовательский.

Отвергнутые альтернативы:

- **GitLab Changelog API / `glab changelog generate`** — даёт те же сабжекты
  коммитов, только сгруппированные, но требует пуша и живого токена и привязывает
  релиз к форджу; общий скрипт умеет ещё и `FORGE=s3`, где этот путь неприменим.
- **Рукописный `CHANGELOG.md`** (Keep a Changelog) — отдельная дисциплина и дубль
  того, что уже видно на странице релиза и в приложении; для соло-проекта
  протухнет первым.

## Решение (июль 2026)

Оставляем текущую схему: сабжекты `/gcm`-коммитов в качестве заметок работают
достаточно хорошо, а цена трейлеров — дисциплина в каждом коммите. Вернуться к
вопросу стоит, если заметки начнут регулярно требовать ручной правки уже после
выпуска релиза — тогда первым шагом делать трейлеры, а не CHANGELOG.md.

Отдельный практический нюанс: многострочный инлайновый `NOTES="…" ./release.sh`
может быть отклонён permission-классификатором агента. Если нужен свой текст —
проще положить его в файл и подставить (`NOTES="$(< notes.md)" ./release.sh`).
